## 今日讨论核心问题

### Q1: 推理能力依赖 LLM，能否真正实现逻辑/因果/数学推理？

| 推理类型 | 现状 | 结论 |
|---------|------|------|
| 逻辑推理 | 本地硬编码规则 + LLM | 本地能做确定性逻辑；复杂多步依赖 LLM |
| 因果推理 | causal.py 硬编码模板 | 简单因果链可以；深层因果依赖 LLM |
| 数学推理 | 几乎全靠 LLM | LLM 的"统计推理"不是真正的"形式推理" |

**核心判断**: USMSB 的推理能力本质上就是 LLM 的推理能力，本地规则层让推理"更稳定、更快"，但不会让推理变得更"聪明"。

### Q2: 加上 skill 自创建能力后，能否自主完成复杂任务？

| 瓶颈 | skill 创建能解决 | skill 创建不能解决 |
|------|----------------|-----------------|
| 记住学会的流程 | ✅ | — |
| 凭空获得新数据源 | — | ❌ |
| 增强 LLM 推理能力 | — | ❌ |
| 动态注册新工具 | ✅ (如果实现动态 tool 注册) | — |

**核心判断**: skill 创建解决的是"记住学到的"，不是"原来不会的"。最终能力上限 = LLM 推理能力 × 工具集丰富度 × skill 积累量。

### Q3: 当前架构不具备泛化能力

```
当前设计的隐含假设：任务相似度 → 策略相似度
实际：表面相似的任务，深层因果可能完全不同
```

**解决方案**: 因果学习系统——发现深层因果结构，而不是表面特征匹配。

### Q4: 需要"学以致用"

```
当前 MetaLearner 只是日志：任务A → 策略B → 成功✓ → 记录
真正的学习：从经验中发现因果规律，能迁移到新任务
```

**需要完整闭环**: 做任务 → 记录经验 → 发现规律 → 生成策略 → 验证泛化 → 固化知识

### Q5: 推理增强的核心方向是什么

```
当前推理方案的问题：
1. 各引擎独立，没有深度融合
2. 推理链路过短（1-2步）
3. 因果推理实际上是模板匹配，不是真正的因果
4. 没有推理过程的自我监控

v2.1 能做到的（工程增强）：
1. 推理步骤显式化（强制 CoT）
2. 多路径一致性检查（Self-Consistency）
3. 反例驱动的自我修正
4. 因果知识的积累和复用

v2.1 不能做到的（算法突破）：
1. 突破 LLM 的推理上限
2. 让 LLM 具备真正的形式推理能力
3. 保证推理 100% 正确
```

**核心定位调整**:
```
不是「让 AI 更聪明」
而是「让 AI 的能力更好地积累和使用」
+ 「让推理过程更透明和可控」
```

## 一、背景与问题

### 1.1 当前 v2.0 的核心缺陷

v2.0 的 evolution_v2 系统包含 MetaLearner、CapabilityAssessor、CuriosityEngine、KnowledgeSolidifier、SelfOptimizer 等组件，代码约 4300 行。但存在根本性缺陷：

```
当前 MetaLearner 的本质：
  「任务A → 策略B → 成功✓」
  → 记录到 SQLite
  → 下次遇到任务A，用策略B

这不是学习，这是日志。
```

**真正缺失的是：**

| 缺失的能力 | 表现 | 后果 |
|-----------|------|------|
| 因果发现 | 不能从经验中发现因果链 | 遇到新任务组合无法迁移 |
| 因果元学习 | 不能快速学会发现新因果 | 每个新领域要大量样本 |
| 因果规划 | 不能在抽象因果空间中规划 | 策略无法跨任务泛化 |
| 因果验证 | 只能试错，无法反事实推断 | 验证成本高，容易踩坑 |

### 1.2 为什么当前架构无法实现"学以致用"

```
当前设计的隐含假设：
  任务相似度 → 策略相似度

实际：
  任务A: [API密集, 数据量小] → 策略B成功
  任务C: [API密集, 超大数据量] → 策略B失败
  
  表面相似（都有API），深层因果不同（数据量决定策略选择）
  
  当前系统会误判：认为任务C也应该用策略B
  因为它只看表面特征，不理解"数据量→策略选择"这个因果链
```

## 二、核心算法设计

### 2.1 因果发现引擎（CausalDiscoveryEngine）

#### 2.1.0 可行性分析

```
⚠️ 高估了纯数据驱动的因果发现

问题：
1. PC Algorithm 需要大量样本（通常数百到数千）
   → TaskRecord 可能只有几十到几百条，不够

2. PC Algorithm 发现的是「统计因果」，不是「机制因果」
   → 只能发现相关性，无法理解深层机制

3. 小样本下条件独立性检验不可靠
   → p-value 检验需要足够的数据支撑

调整后的方案：
1. 降低自动发现预期：重点在「因果知识的表示和存储」
2. 引入先验因果知识（人类提供或 LLM 补充）
3. 小样本时依赖先验，不强求自动发现
4. 因果图作为「可扩展的知识结构」，人工+算法共同维护
```

#### 2.1.1 算法选择：PC Algorithm + 先验知识

```
 alternatives:
   - PC Algorithm: 从条件独立性出发，建因果骨架，再定向
   - FCI Algorithm: 处理隐藏混杂变量（更复杂，当前不需要）
   - GES: 基于评分搜索（需要大数据，当前样本稀缺）
   - NOTEARS: 连续优化方法（适合高维，当前维度有限）

结论：PC Algorithm 作为基础，但必须结合先验知识
  - 有足够样本时：用 PC Algorithm 自动发现
  - 样本不足时：用先验因果知识补充
  - 核心价值：因果知识的统一表示层
```

#### 2.1.3 PC Algorithm 实现

```python
class CausalDiscoveryEngine:
    """
    输入：历史任务记录列表
    输出：因果有向无环图（DAG）
    
    算法流程：
      Step 1: 建骨架（从完全图开始，通过条件独立性检验删边）
      Step 2: 定向边（用 v-结构定向因果方向）
      Step 3: 干预校准（如果有干预数据，定向更准确）
      Step 4: 强度标注（每条边的因果强度）
    """
    
    def discover(self, task_records: list[TaskRecord]) -> CausalGraph:
        # Step 1: 构建特征-策略-效果变量表
        variables = self._extract_variables(task_records)
        
        # Step 2: 计算条件独立性检验表
        # 用条件互信息（Conditional Mutual Information）作为独立性检验
        # CMI(X, Y | Z) = 0 表示 X ⊥ Y | Z
        ci_tests = self._compute_conditional_independence(variables, task_records)
        
        # Step 3: 建骨架（骨架是无向图，表示变量间存在因果/相关关系）
        skeleton = self._build_skeleton(variables, ci_tests)
        
        # Step 4: v-结构定向
        # 规则：如果 X-Z-Y，且 X 和 Y 在 Z 未观测时不条件独立
        # 则定向为 X→Z←Y（Z 是碰撞点）
        dag = self._orient_v_structures(skeleton)
        
        # Step 5: 因果强度估计
        # 用干预数据（如果有）估计每条边的因果效应大小
        dag = self._estimate_causal_strength(dag, task_records)
        
        return CausalGraph(dag)
    
    def _compute_conditional_independence(
        self, 
        variables: list[str], 
        records: list[TaskRecord]
    ) -> dict[tuple[str, str, frozenset[str]], float]:
        """
        计算条件互信息 CMI(X, Y | Z)
        
        实现方式：
        1. 对连续变量做离散化（分箱）
        2. 用卡方检验或 G-test 做条件独立性检验
        3. 返回 p-value，p > 0.05 认为条件独立
        
        关键：需要足够的样本量
        样本量 < 100 时，检验不可靠，需要用更保守的阈值
        """
        pass
    
    def _build_skeleton(
        self, 
        variables: list[str], 
        ci_tests: dict
    ) -> Graph:
        """
        从完全图开始，通过条件独立性检验删边
        
        算法（PC Algorithm 核心）：
        for each edge (X, Y):
            for each subset S of neighbors of X or Y (size = k):
                if CMI(X, Y | S) < threshold:
                    remove edge (X, Y)
                    break
        
        k 从 0 开始，逐渐增加，直到没有边可以删除
        """
        pass
    
    def _orient_v_structures(self, skeleton: Graph) -> DAG:
        """
        v-结构定向
        
        规则：
        如果 X-Z-Y 有边，且 X 和 Y 不相邻，且 Z 不在 separator(X, Y) 中
        则定向为 X→Z←Y
        
        例：
        API调用频率高 → 策略选择 → 执行时长
                      ↑（碰撞点）
        数据量大     ↗
        
        注意：不是所有边都能定向
        未定向边用 ●—● 表示（不知道方向）
        """
```

```python
    target: str          # 果

    confidence: float    # 置信度（边的可靠程度）
    conditions: list[str]  # 适用条件（上下文）
    evidence: list[str]   # 支持证据（来源的任务ID列表）


class CausalGraph:
    """因果图"""
    
    def __init__(self):
        self.nodes: set[str] = set()
        self.edges: list[CausalEdge] = []
        self.undirected_edges: set[tuple[str, str]] = set()
        self.metadata: dict[str, Any] = {}
    
    def add_edge(self, source: str, target: str, **kwargs):
        """添加因果边"""
        edge = CausalEdge(source=source, target=target, **kwargs)
        self.edges.append(edge)
        self.nodes.add(source)
        self.nodes.add(target)
    
    def get_parents(self, node: str) -> list[str]:
        """获取节点的直接因"""
        return [e.source for e in self.edges if e.target == node]
    
    def get_children(self, node: str) -> list[str]:
        """获取节点的直接果"""
        return [e.target for e in self.edges if e.source == node]
```

### 2.2 因果元学习器（CausalMetaLearner）

#### 2.2.0 可行性分析

```
⚠️ 简化版 MAML 实现，优先保证 EWC 稳定性

问题：
1. MAML 需要大量因果任务样本，样本可能不够
2. MAML 的收敛性在少样本下不稳定
3. 端到端的 MAML 实现复杂，调试困难

调整后的方案：
1. 优先实现 EWC（防止灾难性遗忘），这是实打实有用的
2. MAML 部分作为实验性质，不强依赖
3. 重点放在「稳定积累」，而不是「快速适应」
4. 可以用简化的元学习（如策略蒸馏），不用完整的 MAML
```

#### 2.2.1 问题定义

```
当前 MetaLearner 的问题：
  新任务学进来，旧任务的效果下降（灾难性遗忘）
  每个新领域要大量样本才能学会
  
目标：
  学会「发现因果」这个能力本身
  新领域只需要少量样本就能发现因果
  学新因果时保护旧因果不被覆盖
```

#### 2.2.2 算法设计：MAML + EWC

```python
class CausalMetaLearner:
    """
    因果元学习器
    
    外循环：多任务学习，学会「如何发现因果」
    内循环：每个任务快速适应
    
    保护机制：EWC（Elastic Weight Consolidation）
      识别对旧任务重要的参数
      更新时惩罚对这些参数的大改动
    """
    
    def __init__(self, llm_manager=None, knowledge_base=None):
        self.llm = llm_manager
        self.knowledge = knowledge_base
        
        # 因果发现模型的参数（初始为随机）
        self.causal_model_weights: dict[str, np.ndarray] = {}
        
        # Fisher 信息矩阵（记录每个参数对旧任务的重要程度）
        self.fisher_information: dict[str, np.ndarray] = {}
        
        # 每个旧任务的参数重要性
        self.task_importance: dict[str, dict[str, float]] = {}
        
        # 元学习配置
        self.meta_config = {
            "inner_lr": 0.01,       # 内循环学习率（快速适应）
            "outer_lr": 0.001,      # 外循环学习率（慢速更新）
            "ewc_lambda": 5000,      # EWC 惩罚系数
            "meta_batch_size": 5,    # 每个 episode 采样的任务数
            "inner_steps": 5,        # 内循环步数
        }
    
    async def meta_learn(
        self,
        task_distribution: list[CausalTask],
    ) -> MetaLearningResult:
        """
        元学习主循环
        
        CausalTask 结构：
          support_set: 支持集（用来快速适应）
          query_set: 查询集（用来评估泛化）
          domain: 领域标识
        """
        for episode in range(self.meta_epochs):
            # 从任务分布中采样多个任务
            sampled_tasks = random.sample(
                task_distribution, 
                self.meta_config["meta_batch_size"]
            )
            
            total_meta_loss = 0.0
            
            for task in sampled_tasks:
                # ===== 内循环：快速适应 =====
                # 用支持集快速更新，得到任务专用权重
                fast_weights = self._inner_update(
                    task.support_set,
                    self.causal_model_weights.copy()
                )
                
                # ===== 外循环：用查询集评估泛化 =====
                # 在查询集上评估适应后的权重
                query_loss = self._evaluate(
                    fast_weights,
                    task.query_set
                )
                
                # ===== 计算 EWC 惩罚 =====
                # 保护对旧任务重要的参数不被大幅修改
                ewc_penalty = self._compute_ewc_penalty(
                    fast_weights,
                    task.domain
                )
                
                meta_loss = query_loss + self.meta_config["ewc_lambda"] * ewc_penalty
                total_meta_loss += meta_loss
                
                # ===== 更新 Fisher 信息 =====
                self._update_fisher(task.support_set, fast_weights, task.domain)
            
            # ===== 外循环更新 =====
            # 梯度下降更新 meta-weights
            self._outer_update(total_meta_loss / len(sampled_tasks))
        
        return MetaLearningResult(
            final_weights=self.causal_model_weights,
            fisher=self.fisher_information,
        )
    
    def _inner_update(
        self,
        support_set: list[TaskRecord],
        weights: dict,
    ) -> dict:
        """
        内循环：快速适应
        
        用支持集计算梯度，快速更新权重
        这模拟了"面对新任务时快速调整策略"的过程
        """
        for step in range(self.meta_config["inner_steps"]):
            # 计算在支持集上的因果发现损失
            loss = self._causal_discovery_loss(weights, support_set)
            
            # 计算梯度
            grads = compute_gradients(loss, weights)
            
            # 快速梯度下降（高的学习率）
            weights = {
                k: w - self.meta_config["inner_lr"] * g
                for k, w, g in zip(weights.keys(), weights.values(), grads)
            }
        
        return weights
    
    def _compute_ewc_penalty(
        self,
        new_weights: dict,
        current_domain: str,
    ) -> float:
        """
        EWC 惩罚项
        
        计算公式：
        Σ F_i * (θ - θ_i*)²
        
        其中 F_i 是 Fisher 信息（参数重要程度）
        θ_i* 是第 i 个旧任务的优化参数
        """
        penalty = 0.0
        
        for domain, old_weights in self.task_importance.items():
            if domain == current_domain:
                continue
                
            fisher = self.fisher_information.get(domain, {})
            
            for param_name in new_weights:
                theta = new_weights[param_name]
                theta_star = old_weights.get(param_name, theta)
                F = fisher.get(param_name, 0.0)
                
                penalty += F * (theta - theta_star) ** 2
        
        return penalty
    
    def _update_fisher(
        self,
        support_set: list[TaskRecord],
        weights: dict,
        domain: str,
    ):
        """
        更新 Fisher 信息矩阵
        
        Fisher 信息计算：
        F = E[ (∂ log p(y|x,θ) / ∂θ)² ]
        
        用经验 Fisher 近似：
        F ≈ (1/N) Σ (∂ log p / ∂θ)(∂ log p / ∂θ)^T
        """
        # 保存当前任务的重要性（用于 EWC）
        self.task_importance[domain] = weights.copy()
        
        # 计算 Fisher 信息
        fisher = {}
        for param_name, param_value in weights.items():
            # 经验 Fisher 信息
            grads = self._compute_gradients_for_param(
                self._causal_discovery_loss(weights, support_set),
                param_name
            )
            fisher[param_name] = np.mean(grads ** 2)
        
        self.fisher_information[domain] = fisher
```

### 2.3 因果规划器（CausalPlanner）

#### 2.3.1 核心思想

```
当前 TaskExecutor 的问题：
  任务分解是基于「做什么步骤」
  不理解「为什么需要这个步骤」

因果规划器的思想：
  1. 将具体任务抽象为因果子图
  2. 在抽象因果空间中搜索最优策略
  3. 将抽象策略实例化回具体行动

例：
  「分析A股趋势」和「分析加密货币趋势」
  
  表面特征不同：
    A股：数据源=akshare, 品种=股票
    加密货币：数据源=binance_api, 品种=数字货币
  
  深层因果结构相同：
    [价格数据] → [技术指标计算] → [趋势模式识别] → [预测输出]
  
  因果规划器识别这个结构后：
    A股任务的子策略可以直接迁移到加密货币
    不需要重新规划整个流程
```

#### 2.3.2 算法设计

```python
class CausalPlanner:
    """
    因果规划器
    
    在抽象因果空间中规划任务执行策略
    策略可跨任务迁移
    """
    
    def __init__(
        self,
        causal_graph: CausalGraph,
        causal_discovery: CausalDiscoveryEngine,
        llm_manager=None,
    ):
        self.causal_graph = causal_graph
        self.causal_discovery = causal_discovery
        self.llm = llm_manager
        
        # 策略库：每个策略对应的因果效应
        self.strategy_registry: dict[str, StrategyProfile] = {}
    
    async def plan(
        self,
        task: Task,
        constraints: PlanningConstraints,
    ) -> ExecutionPlan:
        """
        规划主流程
        
        输入：
          task: 任务描述
          constraints: 约束条件（时间、成本、质量要求）
        
        输出：
          ExecutionPlan: 可执行的计划
        """
        # Step 1: 任务抽象
        # 将任务描述映射到因果子图
        abstract_graph = self._abstract_task(task)
        
        # Step 2: 目标因果识别
        # 识别任务目标对应的因果末端
        target_nodes = self._identify_target_nodes(abstract_graph)
        
        # Step 3: 因果逆向搜索
        # 从目标出发，逆向搜索需要的因果边
        required_causes = self._backward_search(target_nodes)
        
        # Step 4: 策略选择
        # 选择能激活最多必需因果边的策略
        strategy_sequence = self._select_strategies(
            required_causes,
            constraints
        )
        
        # Step 5: 策略实例化
        # 将抽象策略映射到具体行动
        concrete_plan = self._instantiate_plan(
            strategy_sequence,
            task.context
        )
        
        return concrete_plan
    
    def _abstract_task(self, task: Task) -> CausalSubgraph:
        """
        任务抽象
        
        将具体任务映射到因果子图
        
        实现方式：
        1. 用 LLM 提取任务的关键实体和关系
        2. 在因果图中查找匹配的节点
        3. 提取相关的子图
        """
        # 用 LLM 理解任务结构
        task_structure = await self.llm.analyze(
            prompt=f"""
            分析任务描述，提取关键实体和它们之间的因果关系。
            
            任务：{task.description}
            
            输出格式：
            {{
                "entities": ["实体1", "实体2", ...],
                "relations": [
                    {{"from": "实体1", "to": "实体2", "type": "causal"}},
                    ...
                ],
                "goal": "最终目标"
            }}
            """
        )
        
        # 在因果图中查找匹配
        subgraph = self.causal_graph.extract_subgraph(task_structure)
        
        return subgraph
    
    def _backward_search(
        self, 
        target_nodes: list[str]
    ) -> list[CausalEdge]:
        """
        因果逆向搜索
        
        从目标出发，逆向遍历因果图
        找到所有导致目标的原因链
        
        算法：
        1. 从目标节点开始
        2. 递归查找所有父节点
        3. 构建从因到果的因果链
        """
        required_edges = []
        visited = set()
        
        def dfs(node: str):
            if node in visited:
                return
            visited.add(node)
            
            parents = self.causal_graph.get_parents(node)
            for parent_edge in parents:
                required_edges.append(parent_edge)
                dfs(parent_edge.source)
        
        for target in target_nodes:
            dfs(target)
        
        return required_edges
    
    def _select_strategies(
        self,
        required_causes: list[CausalEdge],
        constraints: PlanningConstraints,
    ) -> list[Strategy]:
        """
        策略选择
        
        选择能覆盖最多必需因果边的策略组合
        
        这是个组合优化问题：
        - 要覆盖所有必需的因果边
        - 要满足约束条件（时间、成本）
        - 策略组合要尽量少
        
        贪心近似：
        1. 每次选择能覆盖最多未覆盖边的策略
        2. 直到所有必需边都被覆盖
        """
        covered_edges = set()
        selected_strategies = []
        remaining_budget = constraints.max_duration
        
        available_strategies = self._get_applicable_strategies(constraints)
        
        while required_causes and remaining_budget > 0:
            best_strategy = None
            best_coverage = 0
            
            for strategy in available_strategies:
                # 计算该策略能覆盖多少未覆盖的边
                coverage = self._calculate_coverage(
                    strategy,
                    required_causes,
                    covered_edges
                )
                
                # 考虑成本效益
                efficiency = coverage / strategy.cost
                
                if efficiency > best_coverage:
                    best_strategy = strategy
                    best_coverage = coverage
            
            if best_strategy is None or best_coverage == 0:
                break
            
            selected_strategies.append(best_strategy)
            covered_edges |= best_strategy.covers_edges
            remaining_budget -= best_strategy.cost
            available_strategies.remove(best_strategy)
        
        return selected_strategies
```

### 2.4 因果验证器（CausalVerifier）

#### 2.4.0 可行性分析

```
⚠️ 简化验证方案，不强求完整的 do-calculus

问题：
1. do-calculus 需要完整的因果图和结构方程模型
   → 实际中因果图不完备，无法做严格推断

2. CausalVerifier 验证的是「策略结果」，不是「推理过程」
   → 无法检测推理过程中的逻辑错误

3. 严格 do-calculus 实现复杂，成本高

调整后的方案：
1. 简化为「模拟执行」：不用严格的 do-calculus
2. 增加「推理过程验证」：要求 LLM 输出结构化推理 + 检查一致性
3. 重点从「验证策略」转向「验证推理步骤」
4. 多路径一致性检查（Self-Consistency）作为主要验证手段
```

#### 2.4.1 为什么需要反事实验证

```
当前验证方式的成本：
  策略A → 执行 → 效果好 ✓  (好结果，但没验证其他策略)
  策略B → 执行 → 效果差 ✗  (浪费一次执行)
  策略C → 执行 → ...       (更多试错)

因果验证的价值：
  「如果不用策略A，而用策略B，效果会怎样？」
  
  不需要真的执行 B
  直接用因果模型推断
  只对高不确定的情况做真实执行
```

#### 2.4.2 算法设计：Pearl 的 do-calculus

```python
class CausalVerifier:
    """
    因果验证器
    
    用反事实推断验证策略
    Pearl 的 do-calculus 实现
    """
    
    def __init__(
        self,
        causal_graph: CausalGraph,
        causal_model,  # 条件概率分布或结构方程模型
    ):
        self.causal_graph = causal_graph
        self.causal_model = causal_model  # P(Y | do(X), Z) 的估计
    
    async def verify_counterfactual(
        self,
        context: VerificationContext,
    ) -> VerificationResult:
        """
        反事实验证
        
        输入：
          context.strategy_a: 策略A（当前已执行的策略）
          context.strategy_b: 策略B（要比较的策略）
          context.outcome_a: 策略A的实际效果
          context.task_features: 任务特征
        
        输出：
          策略B的期望效果，以及是否应该执行验证
        """
        strategy_a = context.strategy_a
        strategy_b = context.strategy_b
        task_features = context.task_features
        
        # Step 1: 识别策略的因果效应
        # 策略是通过激活某些因果边来起作用的
        strategy_a_effects = self._identify_strategy_effects(strategy_a)
        strategy_b_effects = self._identify_strategy_effects(strategy_b)
        
        # Step 2: 计算反事实效果
        # P(效果 | do(策略B), 上下文)
        expected_b = self._compute_counterfactual_effect(
            strategy_b_effects,
            task_features,
            strategy_a.outcome  # 用 A 的实际结果校准
        )
        
        # Step 3: 计算期望差异
        expected_a = strategy_a.outcome.quality
        difference = abs(expected_a - expected_b)
        
        # Step 4: 计算置信度
        # 置信度取决于：
        # - 因果边的置信度
        # - 条件概率估计的可靠性
        # - 上下文与历史任务的相似度
        confidence = self._compute_confidence(
            strategy_b_effects,
            task_features,
            context.historical_records
        )
        
        # Step 5: 决策：是否需要真实执行验证
        should_execute = self._should_execute_verification(
            difference,
            confidence,
            context.verification_cost
        )
        
        return VerificationResult(
            strategy_a_expected=expected_a,
            strategy_b_expected=expected_b,
            difference=difference,
            confidence=confidence,
            recommended_strategy=strategy_a if expected_a > expected_b else strategy_b,
            should_execute_verification=should_execute,
            reasoning=self._generate_reasoning(difference, confidence),
        )
    
    def _compute_counterfactual_effect(
        self,
        strategy_effects: list[CausalEdge],
        task_features: dict,
        observed_outcome: Outcome,
    ) -> float:
        """
        计算反事实效果
        
        用 do-calculus：
        P(Y | do(X)) = Σ_z P(Y | X, Z) * P(Z)
        
        其中 X 是策略（干预变量）
        Y 是效果变量
        Z 是其他上下文变量
        
        具体步骤：
        1. 删除策略X的所有入边（X是自己选的，不是被其他变量导致的）
        2. 保留其他因果边
        3. 用修正后的图计算效果分布
        """
        # 构建干预图：删除 X 的入边
        intervened_graph = self._remove_incoming_edges(
            self.causal_graph,
            strategy_effects
        )
        
        # 计算干预后的效果分布
        # 用 backdoor adjustment 或 frontdoor adjustment
        effect_distribution = self._propagate_intervention(
            intervened_graph,
            task_features
        )
        
        # 返回期望效果
        expected_effect = sum(
            effect * prob 
            for effect, prob in effect_distribution.items()
        )
        
        return expected_effect
    
    def _should_execute_verification(
        self,
        difference: float,
        confidence: float,
        verification_cost: float,
    ) -> bool:
        """
        决策：是否需要真实执行验证
        
        原则：
        - 差异大且置信度高 → 不需要执行，相信推断
        - 差异大但置信度低 → 需要执行验证
        - 差异小 → 不需要执行，差异不够大到值得验证
        - 验证成本高 → 更保守地决定执行
        
        决策阈值：
        - difference > 0.2（20%质量差异）认为显著
        - confidence > 0.8 认为置信
        - cost < 0.3 * difference * base_value 认为值得
        """
        if difference < 0.1:
            return False  # 差异太小，不值得验证
        
        if confidence > 0.85:
            return False  # 高置信，不需要执行
        
        if confidence < 0.5:
            return True  # 低置信，需要执行验证
        
        # 中等置信度，用成本效益决策
        expected_value_of_perfect_info = difference * 1.0  # 假设完美信息的价值
        evpi = expected_value_of_perfect_info
        
        return verification_cost < 0.3 * evpi
```

### 3.0 定位说明

```
⚠️ 新增组件

不是「增强 LLM 的推理能力」
```

### 3.2 多路径一致性检查

```python
class MultiPathConsistencyChecker:
    """
    用多条推理路径的一致性来验证
    基于 Self-Consistency 思想

    不是增加推理能力
    而是检查不同推理路径是否得到相同结论
    """

    def __init__(self, llm, n_paths: int = 3):
        self.llm = llm
        self.n_paths = n_paths  # 成本考虑，用 3 条

    async def verify(
        self,
        task,
        context,
    ) -> ConsistencyResult:
        """
        生成多条推理路径，检查结论一致性
        """
        # 生成多条路径
        paths = await self.llm.generate_multi(
            prompt=task,
            n_paths=self.n_paths,
        )

        # 统计结论分布
        conclusions = [p.final_conclusion for p in paths]
        conclusion_counts = Counter(conclusions)

        most_common = conclusion_counts.most_common(1)[0]
        consistency_score = most_common[1] / len(paths)

        if consistency_score < 0.6:
            # 分歧严重，需要进一步分析
            return ConsistencyResult(
                consistent=False,
                score=consistency_score,
                dominant_conclusion=most_common[0],
                issues=self._analyze_divergence(paths, conclusions),
            )

        return ConsistencyResult(
            consistent=True,
            score=consistency_score,
            dominant_conclusion=most_common[0],
        )

    def _analyze_divergence(
        self,
        paths: list[ReasoningPath],
        conclusions: list[str],
    ) -> list[str]:
        """
        分析分歧原因
        """
        # 找出分歧最大的几步推理
        divergent_steps = []
        for i, path in enumerate(paths):
            for step in path.steps:
                if step.confidence < 0.7:
                    divergent_steps.append(f"路径{i+1} 步骤{step.id} 置信度低: {step.confidence}")

        return divergent_steps
```

### 3.3 反例驱动的自我修正

```python
class CounterexampleDrivenCorrector:
    """
    主动找反例，触发重新推理

    不是验证推理过程
    而是要求 LLM 主动质疑自己的结论
    """

    def __init__(self, llm):
        self.llm = llm

    async def generate_counterexamples(
        self,
        reasoning_step: ReasoningStep,
    ) -> list[Counterexample]:
        """
        问 LLM：「这个结论有没有反例？」
        """
        candidates = await self.llm.generate(
            prompt=f"""
            推理步骤：{reasoning_step.reasoning}

            问：有没有反例可以推翻这个推理？
            如果有，列出 3 个反例。
            每个反例说明：
            1. 反例内容
            2. 为什么这个反例能推翻原推理
            3. 原推理对这个反例的处理方式
            """
        )

        valid_counterexamples = []
        for candidate in candidates:
            if self._is_reasonable_counterexample(candidate, reasoning_step):
                valid_counterexamples.append(candidate)

        return valid_counterexamples

    async def trigger_correction(
        self,
        original_reasoning: ReasoningResult,
        counterexamples: list[Counterexample],
    ) -> ReasoningResult:
        """
        发现反例 → 要求 LLM 重新推理
        """
        return await self.llm.reason(
            prompt=f"""
            原始推理：{original_reasoning.conclusion}
            原始推理过程：{original_reasoning.trace}

            反例：{counterexamples}

            请重新推理：
            1. 承认或反驳这些反例
            2. 如果承认，修改结论或添加限制条件
            3. 如果反驳，说明为什么反例不成立
            4. 输出新的推理过程
            """
        )
```

### 3.4 推理增强器的集成

```python
class ReasoningEnhancer:
    """
    推理增强器

    整合结构化输出、多路径检查、反例修正
    """

    def __init__(
        self,
        llm,
        enable_multi_path: bool = True,
        enable_counterexample: bool = True,
    ):
        self.llm = llm
        self.multi_path_checker = MultiPathConsistencyChecker(llm) if enable_multi_path else None
        self.counterexample_corrector = CounterexampleDrivenCorrector(llm) if enable_counterexample else None

    async def reason(
        self,
        task,
        context,
        require_structured_output: bool = True,
    ) -> ReasoningResult:
        """
        增强推理流程

        步骤：
        1. 生成结构化推理
        2. 检查一致性
        3. 如果有反例，触发修正
        4. 可选：多路径验证
        """
        # 1. 生成结构化推理
        response = await self.llm.generate(
            prompt=self._build_prompt(task, context, require_structured_output),
        )

        trace = self._parse_reasoning_trace(response)

        # 2. 检查步骤一致性
        consistency = self._check_consistency(trace)

        # 3. 反例检查
        if self.counterexample_corrector:
            counterexamples = await self._check_counterexamples(trace)
            if counterexamples:
                # 触发修正
                response = await self.counterexample_corrector.trigger_correction(
                    original_reasoning=response,
                    counterexamples=counterexamples,
                )
                trace = self._parse_reasoning_trace(response)

        # 4. 多路径验证（仅对关键决策）
        if self.multi_path_checker and self._is_critical_decision(task):
            multi_result = await self.multi_path_checker.verify(task, context)
            if not multi_result.consistent:
                # 记录分歧，但不阻断
                logger.warning(f"推理分歧检测: score={multi_result.score}")

        return ReasoningResult(
            conclusion=trace.final_conclusion,
            trace=trace,
            confidence=consistency.confidence,
        )
```

## 四、Skill 自主创建系统（AutoSkillEngine）

### 4.1 概述

Skill 自主创建解决的核心问题：

```
当前问题：
  做任务 → 研究出好方法 → 存在于 context 中
  → 任务结束 → context 消失 → 方法遗忘
  → 下次遇到同类 → 从零开始研究

v2.1 解决：
  做任务 → 研究出好方法 → AutoSkillEngine 创建 skill
  → 持久化到 skills/ 目录
  → 下次遇到同类 → 直接加载 skill → 不需要从零研究
```

### 4.2 触发机制（混合方案）

#### 4.2.1 设计原则

```
代码保证「核心场景不漏」，
Prompt 负责「灵活判断」。

两者配合：
- 代码层：强制触发器，漏判率为 0
- Prompt 层：智能判断，漏判率靠 LLM 能力
```

#### 4.2.2 代码层触发器（固定，必须触发）

| 触发来源 | 触发条件 | 优先级 | 代码位置 |
|---------|---------|-------|---------|
| **任务失败** | TaskExecutor 执行失败 | P0 | `on_task_failed()` |
| **高频任务** | 同一类型任务执行 ≥ 3 次 | P2 | `on_high_frequency()` |
| **因果图缺失** | 因果边没有对应 skill | P1 | `on_causal_edge_missing()` |
| **定时检测** | 每小时检测一次 | P2 | `on_timer()` |

```python
class AutoSkillTrigger:
    """
    代码层强制触发器
    保证核心场景不会漏掉
    """

    def __init__(self, agent, skill_engine):
        self.agent = agent
        self.skill_engine = skill_engine

    def on_task_failed(self, task, error):
        """
        任务执行失败 → 自动触发 create_skill

        代码保证：任务失败必然触发
        不依赖 LLM 判断
        """
        gap = self._analyze_gap_from_failure(task, error)
        if gap:
            self.skill_engine.create_skill_async(gap)

    def on_high_frequency(self, task_type, count):
        """
        高频任务模式 → 自动触发 create_skill

        代码保证：超过阈值必然触发
        """
        if count >= 3:
            gap = self._task_type_to_gap(task_type)
            self.skill_engine.create_skill_async(gap)

    def on_causal_edge_missing(self, causal_edge):
        """
        因果图缺失边 → 自动触发 create_skill

        代码保证：有缺失边必然触发
        """
        gap = self._causal_edge_to_gap(causal_edge)
        self.skill_engine.create_skill_async(gap)
```

#### 4.2.3 Prompt 层触发判断（灵活，LLM 决策）

| 触发来源 | 判断方式 | LLM 职责 |
|---------|---------|---------|
| **失败原因分析** | LLM 分析 | 判断是不是"缺少能力" |
| **知识空白发现** | LLM 反思 | 判断是否值得深入研究 |
| **Skill 质量评估** | LLM 评估 | 判断 skill 够不够好 |
| **优先级排序** | LLM 决策 | 多个缺口先处理哪个 |

#### 4.5.2 SkillDiscovery（缺口发现）

```python
class SkillDiscovery:
    """
    Skill 缺口发现器
    
    发现能力缺口的三种来源：
    1. 因果图发现：某个因果边缺失，没有对应 skill
    2. 好奇心引擎：CuriosityEngine 发现知识空白
    3. 执行失败：MetaAgent 执行任务失败后的反思
    """
    
    def __init__(
        self,
        causal_graph: CausalGraph,
        curiosity_engine: CuriosityEngine,
        task_executor: TaskExecutor,
    ):
        self.causal_graph = causal_graph
        self.curiosity_engine = curiosity_engine
        self.task_executor = task_executor
    
    async def discover_gaps(self) -> list[SkillGap]:
        """
        发现所有能力缺口
        
        返回：需要创建的新 skill 列表
        """
        gaps = []
        
        # 来源 1: 因果图缺失边
        causal_gaps = await self._discover_from_causal_graph()
        gaps.extend(causal_gaps)
        
        # 来源 2: 好奇心引擎知识空白
        curiosity_gaps = await self._discover_from_curiosity()
        gaps.extend(curiosity_gaps)
        
        # 来源 3: 执行失败记录
        failure_gaps = await self._discover_from_failures()
        gaps.extend(failure_gaps)
        
        # 去重：同一个 gap 只保留一个
        gaps = self._deduplicate_gaps(gaps)
        
        return gaps
    
    async def _discover_from_causal_graph(self) -> list[SkillGap]:
        """
        从因果图发现缺口
        
        因果图中的每条边代表一个因果关系
        如果没有对应的 skill 来实现这个关系，就是缺口
        """
        gaps = []
        
        for edge in self.causal_graph.edges:
            # 检查是否有 skill 能实现这个因果边
            has_skill = await self._check_skill_exists_for_edge(edge)
            
            if not has_skill:
                gaps.append(SkillGap(
                    gap_id=f"causal_{edge.source}_{edge.target}",
                    source_node=edge.source,
                    target_node=edge.target,
                    gap_type="missing_causal_link",
                    priority=self._estimate_priority(edge),
                    description=f"缺少实现「{edge.source}→{edge.target}」的 skill",
                ))
        
        return gaps
    
    async def _discover_from_curiosity(self) -> list[SkillGap]:
        """
        从好奇心引擎发现知识空白
        
        CuriosityEngine 追踪各个领域的探索深度
        探索深度低但兴趣高的领域是优先缺口
        """
        gaps = []
        
        domains = self.curiosity_engine.get_domains()
        
        for domain in domains:
            if domain.exploration_depth < 0.3 and domain.interest_level > 0.6:
                gaps.append(SkillGap(
                    gap_id=f"curiosity_{domain.name}",
                    source_node=domain.name,
                    target_node="knowledge",
                    gap_type="knowledge_gap",
                    priority=domain.interest_level,
                    description=f"领域「{domain.name}」探索不足但兴趣高，需要深入学习",
                ))
        
        return gaps
    
    async def _discover_from_failures(self) -> list[SkillGap]:
        """
        从执行失败发现缺口
        
        分析失败记录：
        - 如果是因为缺少某个 skill 而失败 → 发现缺口
        - 如果是 skill 执行错误 → 需要改进 skill
        """
        failures = await self._get_recent_failures()
        
        gaps = []
        for failure in failures:
            if failure.root_cause == "missing_capability":
                gaps.append(SkillGap(
                    gap_id=f"failure_{failure.task_id}",
                    source_node=failure.task_type,
                    target_node=failure.missing_capability,
                    gap_type="missing_capability",
                    priority=1.0,
                    description=f"任务「{failure.task_type}」缺少能力「{failure.missing_capability}」",
                    failed_task_id=failure.task_id,
                ))
        
        return gaps
```

#### 4.5.3 SkillValidator（验证器）

```python
class SkillValidator:
    """
    Skill 验证器
    
    Skill 创建后必须通过验证才能持久化
    验证维度：
    1. 功能正确性：测试用例通过
    2. 因果效应：skill 是否真的激活了对应因果边
    3. 质量评分：prompt 质量、代码质量
    4. 冲突检测：是否与现有 skill 冲突
    """
    
    async def validate(
        self,
        skill: Skill,
        test_cases: list[TestCase],
    ) -> ValidationResult:
        """
        验证 skill
        
        返回：通过 / 不通过 / 需要改进
        """
        checks = []
        
        # 1. 功能正确性
        functional_result = await self._check_functional(test_cases)
        checks.append(("functional", functional_result))
        
        # 2. 质量评分
        quality_result = await self._check_quality(skill)
        checks.append(("quality", quality_result))
        
        # 3. 冲突检测
        conflict_result = await self._check_conflicts(skill)
        checks.append(("conflict", conflict_result))
        
        # 4. 因果效应（如果有因果图）
        if self.causal_graph:
            causal_result = await self._check_causal_effect(skill)
            checks.append(("causal_effect", causal_result))
        
        # 汇总结果
        all_passed = all(r.passed for _, r in checks)
        needs_improvement = any(r.needs_improvement for _, r in checks)
        
        return ValidationResult(
            skill_id=skill.skill_id,
            passed=all_passed and not needs_improvement,
            checks=checks,
            quality_score=self._compute_overall_score(checks),
            issues=[r.issues for _, r in checks if r.issues],
        )
    
    async def _check_functional(
        self,
        test_cases: list[TestCase],
    ) -> CheckResult:
        """
        功能正确性检查
        
        对于 Code Skill：运行测试用例
        对于 Prompt Skill：LLM 评估输出质量
        """
        passed = 0
        failed = 0
        
        for tc in test_cases:
            if tc.skill_type == "code":
                result = await self._run_code_test(tc)
            else:
                result = await self._evaluate_prompt_output(tc)
            
            if result.passed:
                passed += 1
            else:
                failed += 1
        
        return CheckResult(
            passed=passed == len(test_cases),
            needs_improvement=passed < len(test_cases) * 0.8,
            issues=[] if passed == len(test_cases) else [f"{failed} 个测试用例失败"],
        )
```

```python
    """
    Skill 管理者
    
    定期管理和清理 skill 库：
    1. 清理低质量 / 未使用的 skill
    2. 解决 skill 冲突
    3. 合并重复的 skill

        self,
        skill_registry,
        causal_graph: CausalGraph,

        self.registry = skill_registry
        self.causal_graph = causal_graph
        self._cleanup_interval = 86400  # 每天清理一次

        """
        执行 curation 循环
        """
        # 1. 发现低质量 skill
        low_quality = await self._find_low_quality_skills()
        
        # 2. 发现未使用 skill
        unused = await self._find_unused_skills()
        
        # 3. 发现冲突 skill
        conflicts = await self._find_conflicting_skills()
        
        # 4. 发现重复 skill
        duplicates = await self._find_duplicates()
        
        # 统一处理
        for skill_id in low_quality + unused:
            await self._archive_skill(skill_id)
        
        for conflict_pair in conflicts:
            await self._resolve_conflict(conflict_pair)
        
        for duplicate_group in duplicates:
            await self._merge_duplicates(duplicate_group)
    
    async def _find_low_quality_skills(self) -> list[str]:

        - 错误率 > 30%
        - 用户评分 < 3.0

        query = """
        SELECT skill_id FROM skill_registry
        WHERE quality_score < 0.5
           OR error_rate > 0.3
           OR (rating_count > 10 AND avg_rating < 3.0)
```

```python
class AutoSkillEngine:
    """
    自动创建 Skill 引擎
    
    整合所有组件，实现完整的 skill 自创建闭环
    """
    
    def __init__(
        self,
        skill_creator: SkillCreator,
        skill_discovery: SkillDiscovery,
        skill_validator: SkillValidator,
        skill_curator: SkillCurator,
        causal_graph: CausalGraph,
    ):
        self.creator = skill_creator
        self.discovery = skill_discovery
        self.validator = skill_validator
        self.curator = skill_curator
        self.causal_graph = causal_graph
    
    async def run_loop(self):
        """
        自动创建循环
        
        1. 发现缺口
        2. 研究解决方案
        3. 创建 Skill
        4. 验证
        5. 持久化
        6. 管理
        """
        while True:
            # 1. 发现缺口
            gaps = await self.discovery.discover_gaps()
            
            # 按优先级排序
            gaps.sort(key=lambda g: g.priority, reverse=True)
            
            # 2. 处理每个缺口
            for gap in gaps[:self.config.max_skills_per_cycle]:
                try:
                    # 研究解决方案（用 LLM + 工具）
                    solution = await self._research_solution(gap)
                    
                    if not solution:
                        continue
                    
                    # 3. 创建 Skill
                    creation_result = await self.creator.create_skill(solution)
                    
                    # 4. 验证
                    validation_result = await self.validator.validate(
                        skill=creation_result.skill,
                        test_cases=solution.test_cases,
                    )
                    
                    if validation_result.passed:
                        # 5. 持久化
                        await self._persist_skill(creation_result)
                        
                        # 更新因果图（标记这条边已被 skill 覆盖）
                        await self._update_causal_graph(gap, creation_result)
                    else:
                        # 记录失败原因
                        await self._log_creation_failure(gap, validation_result)
                
                except Exception as e:
                    logger.error(f"Failed to create skill for gap {gap.gap_id}: {e}")
            
            # 6. Curator 定期清理
            await self.curator.run_curation()
            
            # 等待下一个周期
            await asyncio.sleep(self.config.cycle_interval)
    
    async def _research_solution(self, gap: SkillGap) -> SkillSolution | None:
        """
        研究解决方案
        
        1. 用 LLM 理解缺口
        2. 搜索外部资源（API 文档、最佳实践）
        3. 生成候选方案
        4. 选择最优方案
        """
        # 用 LLM 分析缺口
        analysis = await self.llm.analyze(
            prompt=f"""
            分析以下能力缺口，设计一个 Skill 来解决它。
            
            缺口：{gap.description}
            类型：{gap.gap_type}
            优先级：{gap.priority}
            
            请设计：
            1. Skill 的名称和描述
            2. 触发条件（什么时候应该调用这个 Skill）
            3. 实现方案（对于 Code Skill：代码；对于 Prompt Skill：prompt 模板）
            4. 测试用例（至少 3 个）
            """
        )
        
        # 搜索外部资源
        if gap.gap_type == "missing_causal_link":
            external_resources = await self._search_external_knowledge(
                gap.source_node,
                gap.target_node
            )
            analysis.integrate(external_resources)
        
        # 生成方案
        solution = await self._generate_solution(analysis, gap)
        
        return solution
```

```python
class ConditionalIndependenceTest:
    """
    完整实现三种检验方法：
    
    1. 条件互信息 (CMI) - 连续变量
       CMI(X, Y | Z) = Σ Σ Σ p(x,y,z) log [ p(x,y|z) / (p(x|z) * p(y|z)) ]
       
    2. 卡方检验 - 离散变量
       χ² = Σ [(O - E)² / E]
       
    3. G-test - 离散变量（更准确）
       G = 2 * Σ [ O * log(O / E) ]
       
    4. 混合变量处理
       - 连续变量离散化（分箱）
       - 使用适当的检验方法
    """
```

2. **骨架构建（skeleton_builder.py）**
```python
class SkeletonBuilder:
    """
    PC Algorithm 骨架构建完整实现：
    
    算法：
    1. 从完全图开始（所有节点两两相连）
    2. 对每条边 (X, Y)：
       对每个大小为 k 的条件集 S：
         如果 CMI(X, Y | S) < threshold:
           删除边 (X, Y)
           break
    3. k 从 0 开始，逐渐增加，直到没有边可以删除
    """
```

3. **边定向（edge_orienter.py）**
```python
class EdgeOrienter:
    """
    v-结构定向 + 边定向完整实现：
    
    1. v-结构识别
       如果 X-Z-Y，且 X 和 Y 不相邻，且 Z 不在 separator(X, Y) 中
       则定向为 X→Z←Y
       
    2. 边定向规则（传散规则）
       规则1：如果 X→Y，且 Y-Z 有边（未定向）
             且 X 和 Z 不相邻，则定向 Y→Z
       规则2：如果 X→Y←Z，则 X→Z
    """
```

### 11.9 关键设计决策

| 决策点 | 选择 | 原因 |
|--------|------|------|
| 因果发现算法 | PC Algorithm | 成熟、理论基础好、适合小样本 |
| 元学习框架 | MAML + EWC | MAML 适合快速适应，EWC 防止遗忘 |
| 推理增强 | CoT + Self-Consistency | 工程可行，不依赖模型能力突破 |
| Skill 存储 | SQLite + 文件 | 与现有 SkillsManager 兼容 |
| 集成方式 | 直接集成到 SelfEvolutionEngine | 组件间需要紧密协作 |
